## Gaps found vs SKILL.md spec + CLAUDE.md hard rules

1. **Spec failure mode "Customer pauses 3rd time in 12 months → convert to
   cancel + offer win-back" was only half-implemented (the headline).** The
   `recentPauses >= 2` branch returned an error and set `jack_tap_required:
   true` — but queued *nothing*. No card reached the outbox, no win-back was
   scheduled, nothing was audit-logged. The "conversion" the spec describes
   never actually happened; the request just died with an error string.
   Fixed by mirroring the refund-handler pattern: a real
   `queueCancelWinbackCard()` writes a `convert_pause_to_cancel_winback`
   Jack-tap card to the Telegram outbox, `next_actions` schedules
   `win-back-campaign-trigger` 30 days out, and the decision is audit-logged
   (see #2). The card write is itself wrapped so a disk failure returns a
   clean error rather than throwing.

2. **CLAUDE.md hard rule 5 (audit-log consequential actions) unmet on the
   pause-limit path.** Converting a customer's pause into a cancel is a
   money-affecting policy decision, but the old branch never called
   `auditLog()`. Now it logs `pause_blocked_converted_to_cancel` with the
   reason, the 12-month pause count, and the MRR at stake — same actor /
   actor_source / skill_invoked convention as the existing success-path
   audit entry.

3. **Correctness: a non-finite `pause_duration_days` produced an Invalid
   Date.** `Math.min(Math.max(req.pause_duration_days ?? 30, 1), 30)` passes
   `NaN`/`Infinity` straight through (`Math.max(NaN, 1) === NaN`), yielding
   `new Date(… NaN …)` — an Invalid Date that then flowed into the
   `02-status.md` entry, the reactivation-prompt timestamp, and the Jack-tap
   card. Same bug class the refund-handler polish (06-15) fixed for refund
   amounts. Guarded with `Number.isFinite()` → falls back to the 30-day
   default. (Verified: a `NaN` duration now yields a valid 30-day date.)

4. **Robustness: malformed `paused_at` dates were silently dropped.**
   `pausesIn12Months` filtered on `new Date(p.paused_at).getTime() > yearAgo`;
   an unparseable date is `NaN`, and `NaN > yearAgo` is `false`, so a corrupt
   history entry vanished from the count — which could let a 3rd/4th pause
   slip past the spec hard-rule-5 floor of 2/year. Now an unparseable
   `paused_at` is counted *toward* the limit (the conservative side: a pause
   that happened is still a pause), with valid dates still date-windowed.

5. **Spec hard rules 1 & 2 (tell the exact reactivation date; never
   auto-cancel) weren't surfaced on the confirmation card.** The Jack-tap
   card stated only "Pause until: {date}". Added an explicit line: "Auto-
   resumes (never auto-cancels) on {date} — billing restarts then," so the
   approval surface itself reflects the resume-not-cancel default.
